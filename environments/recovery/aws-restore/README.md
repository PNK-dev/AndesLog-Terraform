# Restauración regional experimental de RDS

Esta configuración prepara una instancia PostgreSQL desde un backup automático replicado a otra región. Utiliza el workspace HCP Terraform independiente `andeslog-recovery-aws`: no consulta el estado Terraform de la región primaria ni cambia la aplicación. `enable_restore` y `aws_account_id` deben suministrarse explícitamente; sin ellos no se debe poder aplicar. La restauración crea recursos facturables y **no se ha desplegado ni probado en AWS**.

La instancia prevista es privada, Multi-AZ y tiene protección contra borrado. Usa una VPC y dos o más subredes existentes en la región de recuperación. Sin un grupo de seguridad de verificación explícito, la base no acepta conexiones entrantes. Una regla opcional permite TCP 5432 desde ese único grupo, que debe estar en la misma VPC y asignado exclusivamente a un verificador autorizado. La configuración comprueba que las subredes no asignen direcciones públicas automáticamente, pero **esa propiedad no demuestra que sus rutas sean privadas**: revisa tablas de rutas, NACL, grupos de seguridad y DNS antes de utilizarlas.

El backup debe estar disponible en la misma cuenta y región seleccionadas, y su clave KMS debe ser accesible. Se puede solicitar el último punto restaurable o un instante UTC explícito; hay que comprobar que esté dentro de la ventana disponible. Si la región primaria falla, el ARN debe haberse registrado o poder recuperarse desde AWS o el estado remoto de forma independiente. La restauración puede tardar más que el objetivo de 30 minutos y puede no incluir transacciones recientes; se deben medir el tiempo y los datos efectivamente recuperados.

Este root **no hace failover del ERP, no habilita escrituras de negocio, no hace fencing y no prueba integridad ni consistencia de la base**. Para aceptarlo se necesita verificar migraciones, usuarios y datos de negocio con un verificador aislado; además, comprobar RPO, permisos, cifrado, costo y limpieza en una ventana autorizada. No se debe conectar a producción ni anunciar recuperación hasta completar esas pruebas.

El verificador experimental `scripts/verify_erp_restore.py` puede guardar una referencia de solo lectura y compararla con una base diferente. Calcula conteos y SHA-256 sobre columnas seleccionadas de usuarios, almacenes, inventario, pedidos, viajes y outbox, junto con la revisión Alembic. Usa una transacción PostgreSQL `REPEATABLE READ`, rechaza una base en recuperación y exige el host esperado. No guarda los registros ni la contraseña, pero el archivo contiene identidad de la base, conteos y hashes que pueden revelar información por inferencia: protégelo y guárdalo fuera de Git. No incluye los hashes de contraseñas, todas las propiedades de la base ni objetos externos; una coincidencia no demuestra login, integridad completa o ausencia de corrupción.

Para que una comparación exacta tenga sentido, la referencia debe corresponder al mismo punto de datos que se pretende restaurar. Si hubo escrituras o entregas de outbox entre ambos momentos, una diferencia puede ser normal y no prueba pérdida. El instrumento no verifica por sí mismo la procedencia del backup ni la autenticidad de la referencia, no mide RPO y no impide que el origen y el destino sean la misma base mediante alias DNS. Limita filas por tabla, tamaño de fila y tiempo cooperativo; una consulta en curso puede exceder el plazo y una transacción prolongada afecta al mantenimiento de PostgreSQL. El archivo de referencia se crea sin sobrescribir uno existente, pero en Windows el modo Unix no sustituye una ACL privada. Se probó con `pg_dump`/`pg_restore` y datos sintéticos locales, no con RDS ni con identidad o red en AWS.

La ayuda está disponible con `python scripts/verify_erp_restore.py --help` desde la raíz de Terraform. Las conexiones requieren un servicio libpq, archivo de CA y TLS `verify-full`; `capture` crea una referencia nueva y `verify` devuelve `0` solo si la revisión y todas las tablas examinadas coinciden, `2` si difieren y `1` si no se pudo completar la comprobación. Se necesita un rol con `SELECT` limitado a las columnas verificadas y a `alembic_version`. No se deben proporcionar contraseñas como argumentos ni asumir que una referencia queda íntegra sin almacenamiento y controles externos.

## Baja y conservación

Un `plan` o `apply` con `enable_restore=false` puede proponer borrar la restauración previamente creada. No ejecutes cambios sin revisar el plan y confirmar que la cuenta, el workspace y el identificador corresponden a la instancia que se quiere modificar. La protección de borrado viene activada: hay que desactivarla expresamente en una aplicación separada antes de destruir esa instancia. Por defecto se pide un snapshot final, que puede seguir generando cargos después de `destroy`; su nombre incluye `recovery_id` y debe ser único. Omitirlo elimina la base restaurada sin esa copia final y solo debe hacerse cuando se acepta la pérdida de sus datos. Los backups replicados anteriores se gestionan aparte y también pueden seguir facturándose. La baja completa y el comportamiento de esos recursos **aún no se han ensayado en AWS**.

El estado HCP debe protegerse porque contiene identificadores y datos de la infraestructura. Para probar solamente la configuración local, el root se puede inicializar sin backend y ejecutar `terraform test`, que usa el proveedor simulado; eso no demuestra el funcionamiento en AWS. No se requiere ejecutar un `apply` para esas pruebas.
